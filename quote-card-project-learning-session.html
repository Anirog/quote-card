Building and deploying Quote Card

I began with a quote card designed in Sketch and turned it into a small working app one change at a time. The biggest technical change came at deployment: quotes.json could store changes on my Mac, but the live Site needed a database.

1. Project overview

I described the project as a coding demo for practising plain HTML, CSS and browser JavaScript. It was mainly for me, but I also wanted to use it occasionally rather than throw it away once the exercise was over. That explains the way it grew: each change answered a specific usability problem instead of following a large feature plan.

The accessible conversations and Git history show the card gaining random quotes, quote management, refresh and copy controls, a fade between quotes, keyboard shortcuts, navigation, mobile touch targets and a live deployment. Deployment changed how the app runs and stores data. It replaced the original Express server and direct JSON writes with Next.js route handlers and a Sites-managed Cloudflare D1 database.

2. Problems encountered

A static card could not provide a changing collection

The starting point displayed one designed card. Loading quotes from quotes.json made the content change without changing the card's visual design. Later, the refresh button called the same quote-selection code without reloading the page, and the code avoided choosing the current quote again when more than one quote existed.

Editing JSON by hand was awkward

The management page added forms and controls for adding, editing and deleting quotes. The Express server originally handled those requests and rewrote quotes.json. Form validation and escaped output mattered because the page accepted user-entered text and inserted stored quotes back into the page.

Small interactions needed clear feedback

The copy control first changed to the word "Copied!". It was refined several times: the confirmation used Poppins, then included a success icon, and finally became a check-circle icon on its own. The current button changes from the copy icon to a ph-check-circle in #A4B55B for three seconds. Its accessible name changes to "Quote copied" even though no confirmation text is visible.

Keyboard shortcuts had to reuse the button actions safely

n calls showRandomQuote() and c calls copyCurrentQuote(). Reusing those functions keeps mouse and keyboard behaviour together. The listener ignores editable fields, repeated key presses and Command, Control or Alt combinations. The instructions stay fixed at the bottom of the page so the shortcuts are discoverable.

Removing one character changed the spacing

Deleting the middle dot between the shortcut instructions also removed the character's width and its surrounding margins. A 23px left margin on the c key replaced the apparent gap. The session-level record correctly leaves one point open: the old and new gaps looked equivalent, but they were not measured.

The icons were too hard to tap on mobile

The visible icons were 16 pixels and the buttons had no padding. The mobile rule now gives each button a minimum 44px × 44px hit area and uses a 24-pixel icon. The distinction matters: the guideline applied to the tappable button area, not to making the icon itself 44 pixels wide.

Local file storage did not fit the deployment host

The Express version wrote changes directly to quotes.json. Sites could serve the quote viewer, but those file writes would not keep changes made through the deployed management page. Fixing that required Next.js-compatible route handlers, Cloudflare bindings and a D1 database.

Changing a root file did not necessarily change the live page

The deployed app serves the copies under public/, while matching root copies remain in the repository. After the copy-feedback edit, I noticed that the root file had changed but the public site had not. The fix required synchronising both copies, running the build, saving a new Site version and deploying it. A local edit and a live update are separate events.

3. What was tried and learned

Keep early changes small

The refresh button reused the existing card and quote-loading code. The copy button reused the refresh button's CSS. The fade used opacity, a short wait() helper and a guard against overlapping transitions. These were small changes because the local architecture already supported them.

Put shared behaviour in one function

The click handlers and keyboard shortcuts call the same functions. That means a correction to quote selection or clipboard text applies to both forms of input. It also prevents the keyboard version from becoming a second, slightly different implementation.

Treat feedback as state, not decoration

The copy button has a normal state and a temporary success state. The code changes its icon and accessible label, clears an existing reset timer, and restores the normal state after three seconds. This is why the button still communicates success after the visible "Copied" text was removed.

Separate seed data from live data

In the current app, quotes.json supplies the first rows only when the database table is empty. After that, GET, POST, PUT and DELETE use D1 through db/quotes.ts. Editing quotes.json does not update an already-populated live database.

Deployment changed the server and storage

The original project needed only Express, static files and JSON. Sites introduced React, Next.js route handlers, TypeScript, Drizzle schema files, Vite/Vinext and Cloudflare tooling. Most of the user-facing page stayed plain HTML, CSS and JavaScript. The extra code exists mainly because persistent storage and the hosting environment require it.

Verification became more specific as the project grew

Some early changes ended with a code review and a suggested browser check. Later work used production builds, local browser interaction tests, file comparisons between root and public/, and deployment-status checks. The copy feedback test checked the icon class, colour, size, missing text and timed reset rather than merely checking that the page loaded.

One failed approach worth keeping: changing only the root quote-card files was not enough once Sites served public/. The files could look correct locally while the deployed source remained unchanged.

4. Connected concepts

Interaction design and code structure

The refresh and copy controls each involve more than an icon. An event starts the action, the page updates, an accessible label reports the state, and a timer restores the copy button. Buttons and keys call the same functions, so this code stays in one place.

Visible size, hit area and accessibility

A 24-pixel glyph can sit inside a 44-pixel button. The first value controls what the icon looks like; the second controls how easy it is to tap. Accessible names let the icon-only buttons retain a clear meaning for assistive technology.

Source files, built output and deployed state

Updating the live page takes several separate actions. Edit the maintained files, make sure duplicate copies match, build the app, save a version and deploy it. The update is confirmed only after the host reports success and the served page is checked.

Data model and API design

The browser still addresses quotes by array position. The database stores each quote with an integer ID, and quoteIdAt() translates a requested index into that ID before updating or deleting a row. This preserves the old browser API, but it ties operations to the current sort order.

The pages stayed simple while the hosting code grew

The visible quote pages remain close to the original plain HTML, CSS and JavaScript. The repository is no longer a plain Express app, though. The hosting adapter, route handlers and database layer now do work that server.js and quotes.json once handled locally.

5. Knowledge gaps

Where live data comes from

Evidence: I later asked where the live site's quotes were stored. The important distinction is now clear: quotes.json seeds an empty D1 table; it is not the live store after deployment.

Why it matters: without this distinction, I could edit the repository's JSON file and expect existing live data to change.

Which file is the source of truth

Evidence: after the icon change, I reported that the root file had the change but the public site did not. The repository currently keeps matching root and public/ copies of three front-end files.

Why it matters: duplicated files make it possible to test or edit one copy while deploying another. Comparison checks currently catch this because the repository does not have one source file for each page.

How to verify browser behaviour

Evidence: several early tasks ended without a browser test, while later tasks checked the rendered state and timed reset directly. The existing spacing record also says the old and new gaps were never measured.

Why it matters: a successful build cannot prove that a touch target is usable, a fade feels right, a gap stayed the same, or a button resets after three seconds.

Stable record identifiers

Tentative gap: the current API accepts an array index and converts it to a database ID. The available conversations do not show a problem caused by this, but the mapping could target a different row if ordering or filtering changes later.

The boundary of the project

Unresolved: the project interview established that this was my coding demo, mainly for me, and that I wanted occasional personal use. I stopped the interview before deciding whether the front end, server, deployment or database should be the main subject from this point onward.

6. Recommended learning path

The first three steps address questions and problems that appeared in this project. The last step is optional unless quote ordering or concurrent editing becomes important.

1. Follow one quote through the whole app

Why
This closes the gap between the static page, API and live database.
Understand
How form input becomes a POST request, a bound SQL insert and a row returned by the next GET.
Connection
It explains exactly why quotes.json and live D1 data are different.
Exercise
Add a uniquely worded test quote locally, identify the request that created it, then find the code that reads it back.

2. Map the path from an edit to the live Site

Why
The root/public mismatch caused a real deployment problem.
Understand
Which files the browser receives, what the build checks, and why saving and deploying a Site version are separate steps.
Connection
It explains why a correct root file did not update the public page.
Exercise
Change one harmless piece of local text, predict every generated or copied file that should change, and verify the prediction before deployment.

3. Practise interaction checks in the browser

Why
The project contains timing, focus, clipboard and responsive behaviour that a build cannot check.
Understand
The difference between code validation, rendered layout checks and interaction tests.
Connection
This covers the fade, keyboard guards, mobile hit areas, copy feedback and spacing question.
Exercise
Write a short manual test with exact expected states at 0 seconds and 3 seconds after copying, then run it at desktop and mobile widths.

4. Optional: use database IDs in the browser API

Why
Database IDs keep an edit attached to one quote even if list order changes.
Understand
The difference between a row's identity and its current position in a displayed list.
Connection
The current quoteIdAt() helper translates positions into IDs on the server.
Exercise
Sketch the JSON returned by GET /api/quotes if it included IDs, then describe how the edit and delete URLs would change.

7. Key takeaways

  • A useful project can grow through small, specific requests without beginning as a large application plan.
  • Buttons and keyboard shortcuts should call the same functions so their behaviour does not drift apart.
  • An icon's visible size and its tappable area solve different problems.
  • quotes.json was once the data store. It is now seed data; D1 stores the live quotes.
  • A local change, a successful build and a deployed update are three different states.
  • The current front end is simple to read, but the deployed project has more infrastructure than the original Express version.

8. Questions to revisit

  • Should the duplicated root and public/ files remain, or should one set become the only maintained source?
  • Should the management page edit quotes by database ID rather than current list position?
  • What is the smallest useful set of repeatable browser tests for refresh, copy, shortcuts and quote management?
  • Does the 23px shortcut gap match the old separator when measured, or does it only look close?
  • Is the project now mainly a front-end learning exercise, a personal quote tool, or a way to learn deployment and persistence?
